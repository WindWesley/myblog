只有一个获取电量的方法时，手写 MethodChannel 很直接。等到支付、定位、相机都接进来，方法名、参数结构和错误码散落在两端，修改一个字段就开始依赖口头同步。

Pigeon 值得引入的地方就在这里：把两端共同遵守的接口写在一处，再生成通信代码。它减少的是重复维护协议的工作，不会替你完成原生实现。

## 契约先描述数据，再考虑传输

电量是数字，就不要为了传输方便返回字符串。无法获取电量是一种失败，也不应该悄悄变成字符串 "null"。

下面是契约文件的最小示例，需要交给 Pigeon 生成代码，不能直接当成业务层实现：

```dart
import 'package:pigeon/pigeon.dart';

@HostApi()
abstract class BatteryApi {
  int getBatteryLevel();
}
```

生成之后还要在原生端实现接口，并注册到正确 FlutterEngine 的 messenger。新增原生代码需要重新构建应用，热重载不足以完成接入。

业务层最好再包一层 BatteryService，将原生异常转成应用能理解的失败类型。这样页面不用知道通信通道的名字，也不用到处解释平台错误码。

## 编译通过，只解决了一部分问题

Pigeon 能帮助发现接口签名不一致，却不能保证权限已授予、设备支持该能力，或者原生实现没有遗漏注册。MissingPluginException 也不只有方法名拼错一个原因。

排查时可以沿一条固定路径走：实际运行的平台是否支持这个方法，当前引擎是否注册了处理器，调用名称和编码是否匹配，构建产物是否包含最新原生实现。混合开发涉及多个引擎时，尤其要确认注册对象。

两端代码应由同一版本的 Pigeon 生成，并一起提交。生成的通信协议属于内部实现，不应默认不同生成器版本能够互通。[Pigeon 官方说明](https://pub.dev/packages/pigeon)

## 可以逐步迁移，不必一次替换所有模块

Pigeon 与手写 MethodChannel 可以在不同通道上共存。真正要避免的是重复注册同一个通道，或者只替换了一端却继续使用不兼容的协议。

可以先迁移一个边界清楚的模块：保留业务调用入口，替换下面的通信实现，验证成功、失败和未支持平台三条路径，再继续下一个模块。不要手改生成文件来兼容旧逻辑，否则下次生成时改动会丢失。

## 异步返回，不代表后台执行

Dart 侧 await 一个调用，只表示等待结果时不会同步阻塞 Dart 调用栈，不代表原生处理函数自动跑在后台。读取大文件、压缩图片等耗时工作仍要按平台要求调度；涉及 UI 的操作也要回到相应线程。

Flutter 提供后台 Task Queue 等机制，具体要结合平台和使用的 API。不要用一个 Flutter 版本号概括所有线程行为。[平台通道与线程说明](https://docs.flutter.dev/platform-integration/platform-channels)

迁移的完成标准不是“字符串少了”，而是两端接口能一起演进，错误能回到调用方，耗时工作不会堵住界面。
