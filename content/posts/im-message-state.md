自己发出一条消息时，气泡先出现“发送中”，收到回执后变成“已发送”。如果实现方式是删除旧对象、再插入服务端对象，列表里可能短暂出现两条，局部动画和滚动位置也容易受影响。

项目的 `ChatMessage` 已经用 ValueNotifier 管理发送状态，`MessageView` 按文字、图片、语音、文件等类型选择内容组件。这是两个值得保留的边界：发送状态不必让整页重建，消息类型也不必让列表组件知道内部布局。

### 先约定稳定的 UI 身份

发送前可以生成一个本地 ID，服务端确认后再建立本地 ID 与服务端 ID 的关联。在同一条消息的生命周期里，列表 key 保持稳定，更新内容和状态即可。

这不是说永远忽略服务端 ID。它仍然用于同步、撤回和去重；只是“当前组件是哪一条消息”不应随着发送成功突然变化。

状态至少要能表达发送中、成功和失败。重试时还要确认协议是否支持幂等发送，避免同一内容被服务端接受两次。

### 分清结构更新与局部更新

项目通过广播流发送消息列表，也通过 ValueNotifier 更新单条状态。两种通道可以共存，但需要明确分工：

```text
增加、删除、重新排序 → 发布列表结构快照
发送状态、上传进度 → 更新对应消息的局部状态
正文被编辑、消息被撤回 → 更新内容，并重新计算相关展示行
```

发布结构快照时，不宜反复把同一个可变 List 对象交出去。可以使用 `List.unmodifiable(messages)` 固定本次列表成员和顺序；其中的消息对象仍可能变化，因此这不是整个对象树的深度不可变。

ValueNotifier 的生命周期也要有归属。消息从存储和界面彻底移除后才能释放，不要在暂时离开视口时就 dispose，因为列表还可能再次构建它。

### 未识别类型也需要占一行

目前 MessageView 的初始值是空组件。遇到新协议类型，静默不显示会让用户误以为消息丢了。更合适的回退是一个“暂不支持此消息”的轻量气泡，保留消息时间与基本交互能力。

另外，撤回会改变相邻气泡的姓名、头像或日期组合。局部状态更新虽小，也不能完全脱离上下文。可以在展示行整理阶段计算这些相邻关系，避免每个气泡反复到全局列表中查找自己。
