请求返回了 200，页面却不能继续。这在带业务码的接口里很正常：传输成功，不代表操作被接受。

项目在 `customAnalysis` 里集中解释业务码，这一步值得保留。各个页面不必反复判断同一组字段，后端调整协议时也有明确的修改位置。但公共分析入口还要避免把所有失败压成一种结果。

例如用户离开页面后取消请求，通常不需要弹错误；服务拒绝了某个操作，原样重试也未必有效；临时超时，才可能适合给用户一个重试入口。

### 错误分类的先后有影响

使用 Dio 时，可以先识别取消与超时，再根据是否收到响应解释 HTTP 和业务状态。以下是处理顺序示意，不依赖某个接口的成功码：

```text
主动取消 → cancelled
连接或收发超时 → timeout
收到响应 → 校验响应结构，再按该服务协议解释
没有响应 → network
成功响应无法解析成模型 → decoding
```

顺序不能机械照搬到所有异常：如果 SDK 同时提供了响应与异常，还需要按其语义决定是否采用响应。关键是别让“异常存在”直接覆盖掉更具体的信息。

项目虽然定义了取消枚举，读到的执行路径里却没有明确把 Dio 取消映射过去。改进时应把这个分支接完整，而不是只给结果类型增加名字。

### 重试需要考虑副作用

文章列表读取失败后重新拉取，与提交订单超时后重试，不是同一件事。超时只说明客户端没有及时拿到结果，不说明服务端没有执行操作。

对带副作用的请求，先确认服务端是否支持幂等标识或结果查询。没有这些约定时，不要在通用拦截器里无限重发。对于允许重试的读取请求，也应该限制次数，采用退避，并在取消后停止。

鉴权清理同样需要协议依据。当前代码对 400、401 都有清理动作，抽成公共层时应该收窄到明确的会话失效信号；普通参数错误不应让用户突然退出登录。

### 错误信息最终交给谁

基础层保留错误类型、可展示信息和诊断信息，页面选择呈现方式。首次加载失败显示错误页，后台刷新失败保留旧数据，表单错误尽量靠近对应输入项。这样既能共用请求代码，也不会把每个场景都做成同一个弹窗。
