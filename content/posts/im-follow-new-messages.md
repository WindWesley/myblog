正在翻前一天的聊天记录，底部来了三条新消息，列表突然把人带回最新一条。这种行为在功能上没有“丢消息”，阅读却被打断了。

项目已经做了一个很实用的区分：接近底部时，新消息直接显示并跟随；离开底部后，消息先放入待展示集合，同时增加新消息计数。自己发送消息则主动回到最新位置。

这个设计值得保留。决定是否跟随的依据，是用户当前的阅读意图，而不是“收到事件就滚动”。

### 在更新列表之前判断位置

对于竖直、反向且最新消息位于底部的列表，可以把“离最新端的距离”写成一个明确函数：

```dart
bool isNearLatest(ScrollController controller, {double threshold = 64}) {
  if (!controller.hasClients) return false;
  final position = controller.position;
  if (!position.hasContentDimensions) return false;
  return (position.pixels - position.minScrollExtent).abs() <= threshold;
}
```

这里假定控制器只连接一个滚动视图。阈值用逻辑像素，并不是必须精确到零的判断；列表处于轻微回弹时，也不会立即改变策略。

顺序很重要：先记录是否接近最新端，再合并数据。合并以后布局长度已经变化，原来的阅读位置不一定还能从新距离还原出来。

### 等布局，不猜一个固定延时

项目的回到底部通过 300 毫秒 Timer 触发。固定等待无法保证图片已经完成布局，也可能在用户再次滑动后才执行。

可以在提交状态后安排帧后回调，再检查页面是否仍然存活、控制器是否挂载，以及用户是否已经开始新的滚动手势。只有这次跟随意图仍然有效，才滚到最新端。

帧后回调只说明这一帧布局已完成，不说明所有图片都已确定尺寸。消息图片提前预留大小，会让这套策略可靠得多。相关布局时机见 [ScrollController 文档](https://api.flutter.dev/flutter/widgets/ScrollController-class.html)。

### 新消息提示不是服务端未读数

“下方有 3 条新消息”描述的是当前视口没有展示的内容。服务端未读数还可能受其他设备、已读回执和会话状态影响。两者应分开维护。

若收到重复推送，同一消息不能再加一次计数；若缓存中的消息被撤回，也要同步更新待展示集合。点提示按钮时，一次合并、一次滚动、一次清理提示，避免逐条插入带来连续跳动。
