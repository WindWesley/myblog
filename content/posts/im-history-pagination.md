滚动到顶端加载历史，很容易写成：判断位置、设 loading、发请求、插入结果、清掉 loading。

项目里使用了防重复标志，并在请求后额外等待两秒。这个延时能压住短时间内的重复触发，但不能替代请求的状态管理。遇到异常，如果清理语句没执行，加载标志可能一直停在那里。

### 先把一次加载关完整

下面是状态逻辑示意。`fetchOlder` 返回服务端或 SDK 定义的一页，`merge` 负责按稳定消息身份合并，外部仍需提供异常展示：

```text
如果正在加载，或明确没有更多历史：返回
记录当前会话 ID、加载代次和请求游标
设置 loading
try:
    page = 等待 fetchOlder(请求游标)
    如果会话或加载代次已变化：丢弃响应
    merge(page.messages)
    更新 nextCursor 和 hasMore
catch:
    当前加载仍有效时，记录可重试错误
finally:
    只有当前加载仍有效时，清理它的 loading
```

会话和代次检查不仅用于列表数据，也用于错误和 loading。切到另一个群以后，旧群的失败回调不应该把新群的加载状态关掉。

### 时间戳能否做游标，要看接口契约

当前实现取最早一条消息的发送时间继续查历史。这是已有 SDK 调用方式，但时间戳本身未必唯一：多条消息可能有相同时间。

因此，需要确认查询边界是否包含该时间点、是否有稳定的次级排序，以及接口是否另有消息 ID 或游标。客户端去重可以消除重叠页，却不能挽救服务端分页条件本身跳过的消息。

如果连续两次响应都没有让游标前进，不要无限请求。可以停止这轮自动加载并记录异常，保留手动重试；这与明确宣布“没有更多历史”不是同一个状态。

### 触发区域比精确相等更稳妥

监听 `pixels == maxScrollExtent` 对回弹和尺寸变化较敏感。可以定义一个接近历史端的区域，在区域内尝试加载，由互斥与 hasMore 防止重复。

首次内容不足一屏时，用户未必能产生滚动事件。若产品希望补满一屏，可以在布局后有限次数地继续拉取，同时检查游标是否推进。不要用无限循环把整个聊天历史一次性下载下来。
