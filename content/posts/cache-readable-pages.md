重新打开一个看过的页面，如果网络暂时不可用，之前的内容不应该凭空消失。项目把响应缓存接进请求链路，正是在解决这个问题：先有一份可读数据，再尝试得到更新。

不过，“先有”是体验目标，不代表代码天然保证缓存回调先执行。当前缓存读取与网络请求都会往下游分发，缓存读取没有被等待。如果磁盘读取较慢，旧缓存也可能晚到。

### 一份响应副本，至少带上保存时间

现在的缓存管理器主要保存 Map。进一步整理时，可以增加一个很小的信封：

```json
{
  "schemaVersion": 1,
  "savedAt": "2024-09-18T08:00:00Z",
  "data": {"items": []}
}
```

这不是要求每个页面实现一套规则。由缓存层检查结构版本，由接口策略决定过期时长。过期内容是直接丢弃，还是作为旧内容展示并标明状态，应由数据用途决定。频繁变化的数据通常比静态介绍页更需要谨慎。

### 缓存失败不该拖垮网络成功

当前写入发生在请求返回前，而且未先限定业务成功。更适合多数读取接口的顺序，是先完成业务校验和模型解析，再尝试缓存有效响应。缓存写入失败可以记录，但不要因此把已经可用的网络结果变成页面错误。

同样，损坏的缓存应被当作未命中，继续尝试网络，而不是终止整个请求。

### 同一次加载，只接受合理的新旧关系

可以给每次页面加载分配编号，并维护该次加载是否已接受网络结果：

```text
缓存返回：编号仍有效，且本轮尚未接受网络结果 → 展示
网络成功：编号仍有效 → 展示，并标记已接受网络结果
网络失败：保留本轮已经展示的缓存，标记刷新失败
切换查询或账号：更换编号，旧回调不再影响页面
```

如果缓存刻意选择串行读取，也要给磁盘操作合理的失败处理，不能让缓存一直阻塞网络。

缓存键则应包含环境、请求方法、路径、规范化参数和账号作用域。仅仅把 Map 转成字符串拼接，可能让等价参数生成不同键；直接拼入访问凭证也不合适。

项目已有首屏缓存开关，可以继续沿用。但它还不是完整的离线同步：没有缓存的首次访问仍然需要网络，离线提交、冲突合并和重放队列都属于另外的问题。
